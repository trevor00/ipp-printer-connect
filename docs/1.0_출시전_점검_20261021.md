# 1.0 출시 전 코드 점검

점검일: 2026-10-21
대상: 작업 폴더의 0.9.13 / versionCode 103 소스
판정: 현재 상태에서 1.0 확정 보류

후속 수정: 이 문서는 0.9.13 점검 당시의 기록이다. 지적 항목에 대한 0.9.14 코드 수정과 남은 지원 한계는 [0.9.14 수정 내역](0.9.14_수정내역.md)을 참고한다. 사용자가 흑백 기본값은 유지하도록 지정했다. 수정 후 실기 검사는 별도로 필요하다.

## 점검 기준과 범위

사용자가 선택하지 않은 내용 변경, 품질 저하, 설정 무시가 있는지 확인했다. 문서 선택 → 변환 판단 → 페이지 생성 → IPP 옵션 작성 → 전송 → 결과 표시와 미리보기·메모리 처리를 추적했다.

이번에는 소스를 읽고 기존 검증 기록을 확인했다. 앱 코드와 버전은 변경하지 않았으며, 빌드·테스트·휴대폰 조작·프린터 전송은 실행하지 않았다. 아래의 '확인'은 코드 경로 확인을 뜻하며 실제 종이 출력으로 재현했다는 뜻은 아니다. 작업 폴더에는 기존 수정 및 미추적 파일이 있으므로 GitHub의 마지막 커밋에 대한 평가도 아니다.

## 우선 수정해야 하는 항목

### 1. PDF 페이지 번호 선택이 내용 배치 변경으로 처리됨

- 근거: MainActivity.kt:2459, 2765 / FileDocumentPreparer.kt:167 / DocumentRenderer.kt:179, 199.
- 조건: PDF에서 내용 크기·여백을 바꾸지 않고 페이지 범위만 지정한다.
- 현재: 페이지 범위도 hasExplicitLayoutRequest에 포함된다. 이 값이 contentLayoutChanged로 전달되어 PDF 전체를 선택 용지·기본 맞춤·기본 내부 여백으로 다시 그린 뒤 페이지를 추린다.
- 영향: '2페이지만 출력'이 원래 2페이지의 내용 크기·여백까지 바꾸고 글자·벡터를 픽셀로 만드는 동작이 된다. 모아찍기도 같은 구분 문제를 갖는다.
- 수정 기준: 내용 배치 변경과 페이지 추출·모아찍기를 구분한다. 페이지 추출만으로 크기·여백을 바꾸지 않는다. PDF 원본 객체를 보존하는 페이지 추출이 필요하다. 이미지화가 필요한 경로는 그 사실과 해상도를 명시한다.

### 2. PDF 형식 변환에서 선택한 IPP 맞춤·위치가 사라질 수 있음

- 근거: MainActivity.kt:2459, 3083 / FileDocumentPreparer.kt:167 / PrintWorkManager.kt:134 / PrintLayoutSupport.kt:9.
- 조건: PDF를 지원하지 않는 프린터에 PostScript 등으로 변환하고, '내용 크기 맞춤' 또는 고급 IPP 가로·세로 위치만 변경한다.
- 현재: 이 세 옵션은 내용 배치 변경 판정에 포함되지 않는다. 원본 PDF를 그대로 렌더링한 후, 변환 결과라는 이유로 IPP 맞춤·위치를 none/center 등으로 바꾼다.
- 영향: 사용자가 고른 맞춤·위치가 문서에도 반영되지 않고 프린터에 보내는 옵션에서도 사라질 수 있다.
- 수정 기준: 각 옵션을 앱과 프린터 중 누가 적용했는지 구분하고, 앱이 실제 적용한 옵션만 전송 시 중립값으로 바꾼다.

### 3. PostScript MIME 별칭에서 압축 설정이 숨겨지고 이전 값이 적용될 수 있음

- 근거: DocumentOutputPlanner.kt의 conversionTargets / MainActivity.kt:2537, 2564, 3103 / PrintFormatSupport.kt의 normalize.
- 조건 예: 프린터가 image/jpeg와 application/x-postscript를 광고한다. JPEG 변환에서 품질 90을 선택한 다음 PostScript로 바꾼다.
- 현재: 변환 목록은 광고 MIME 원문을 보관한다. UI는 application/postscript와 문자열이 정확히 같은 경우에만 압축 선택기를 초기화하고 표시한다. 실제 전송 설정은 MIME을 정규화한 뒤 같은 선택기 인덱스를 읽는다.
- 영향: 별칭 PostScript에서는 압축 선택기가 숨겨지고, 남아 있던 인덱스 1이 PostScript JPEG 100으로 해석되어 손실 압축이 적용될 수 있다. JPEG 100도 무손실은 아니다.
- 수정 기준: UI 판단에는 정규화한 MIME을 쓰고, 전송 헤더에만 광고 원문을 쓴다. 압축 설정을 형식별 실제 값으로 저장하며 형식 변경 시 값과 표시를 일치시킨다.

### 4. PDF 출력에서도 글자·벡터가 이미지로 바뀌지만 설명이 부족함

- 근거: DocumentRenderer.kt:179, 199 / MainActivity.kt:2442.
- 현재: PDF 배치와 모아찍기는 페이지를 픽셀로 그려 새 PDF에 넣는다. PDF라는 확장자가 유지돼도 글자·벡터 구조는 유지되지 않는다. 선택한 DPI가 보이지만 PDF 변환 설명에는 이 변화가 없다.
- 영향: 사용자는 PDF→PDF이므로 품질과 문서 구조가 유지된다고 생각할 수 있다. 무손실 RGB/Flate 압축은 생성한 픽셀을 무손실로 저장한다는 뜻이지, 원본 PDF를 무손실로 보존한다는 뜻이 아니다.
- 수정 기준: 페이지 추출·이동·크기 조절을 가능하면 PDF 객체 수준에서 처리한다. 픽셀화가 필요한 경우에는 해당 경로와 변화를 짧게 표시한다.

### 5. 일부 용지와 여백을 추정값으로 출력에 사용함

- 근거: MainActivity.kt:2193, 2860, 3099, 3151.
- 현재: 용지 이름을 해석하지 못하거나 기본 용지 정보가 없으면 595×842pt(A4)로 처리한다. 여백은 매체별 정보가 아니라 전체 지원 값 중 최소 양수값을 선택한다. '프린터 광고 여백 사용'에서는 좌·상·우·하 중 최댓값을 네 변에 동일하게 적용한다. 여백 광고가 없으면 출력 가능 영역을 5mm로 가정한다.
- 영향: 실제 선택 용지와 내부 변환 용지가 다르거나, 표시한 좌우 여백과 실제 적용 여백이 달라질 수 있다. 5mm는 화면 표시만이 아니라 PRINTABLE_FIT 변환에도 사용된다.
- 수정 기준: 알 수 없는 용지 크기는 사용자 확인 없이 A4로 대체하지 않는다. 용지별 실제 속성과 추정값을 구분하고, 추정을 출력에 적용한다면 그 사실이 선택지에 드러나야 한다. 비대칭 여백을 그대로 적용한다.

### 6. IPP 설정 무시·대체 경고를 일반 성공으로 표시함

- 근거: IppClient.kt:341, 384, 440, 507, 685 / MainActivity.kt:3070 부근.
- 현재: 0x0000~0x00ff를 모두 성공으로 처리한다. 옵션 무시·대체(0x0001), 충돌에 따른 대체(0x0002)도 일반 접수 성공으로 표시한다. Validate-Job에는 ipp-attribute-fidelity가 없고 경고 성공을 허용한다. 응답 파서는 속성 그룹도 보존하지 않는다.
- 보완된 부분: 실제 작업 생성 요청에는 ipp-attribute-fidelity=true를 보낸다. 따라서 정상적인 프린터에 설정 엄수를 요청하는 장치는 이미 있다. 다만 반환된 경고를 처리하는 방어는 부족하다.
- 추가 문제: 응답이 속성 중간에서 잘리면 파서가 오류 대신 반복문을 끝내고 앞부분의 성공 상태를 반환할 수 있다.
- 수정 기준: 사전 검증에서 대체·충돌을 발견하면 문서 전송 전에 중단한다. 제출 후 경고는 실제 접수 상태를 유지하면서 변경 가능 항목을 명확히 알린다. 잘린 응답은 '결과 확인 불가'로 구분한다. 이미 접수됐을 수 있는 작업을 단순 실패로 처리하거나 자동 재전송하지 않는다.
- 표준 근거: RFC 8011, B.1.2.1~B.1.2.3 및 ipp-attribute-fidelity 설명.
  https://www.rfc-editor.org/rfc/rfc8011.html

## 실사용 신뢰성을 위해 함께 정리할 항목

### 7. 같은 배치 항목을 두 곳에서 설정하고 우선순위가 보이지 않음

- MainActivity.kt:3083의 selectedContentLayout은 고급 IPP 위치와 '내용 크기 맞춤' 값을 페이지 배치의 정렬·크기보다 우선한다.
- 예: 고급 가로 위치가 왼쪽이면 페이지 배치에서 오른쪽을 골라도 왼쪽으로 해석한다.
- 해결: 같은 기능의 조작을 하나로 통합하거나 서로 동기화한다. 사용자에게 표시되는 값과 실제 유효값이 다르면 안 된다.

### 8. 미리보기는 최종 색상·출력 형식을 검증하지 않음

- FileDocumentPreparer.preview는 중간 PDF를 보여준다. PCL의 1비트 흑백 처리나 JPEG 재압축은 실행하지 않는다. 색상 모드는 변환 후보 판단에는 사용되지만 화면을 흑백으로 만드는 데 사용되지 않는다.
- PCL 변환은 DocumentRenderer.kt:428에서 밝기 170 기준으로 흑백화한다. 미리보기에서 보인 회색 글자·옅은 선이 최종 PCL에서는 없어질 수 있다.
- 원본 PDF 미리보기는 원본 페이지 비율을 사용하면서 설명에는 선택한 실제 용지 경계라고 표시한다. 원본 페이지와 선택 용지 크기가 다르면 정확한 용지 배치 미리보기가 아니다.
- 해결: 배치 미리보기의 범위를 정확히 표시하고, 출력에 영향을 주는 흑백/PCL 변화는 화면에도 반영한다. 원본 페이지와 출력 용지를 구분한다. 낮은 화면용 해상도를 사용하는 것은 유지해도 된다.

### 9. Raster 형식의 세부 지원 조건을 확인하지 않음

- IppClient.kt:72의 조회 목록에는 PWG Raster 문서 해상도·색상 유형·뒷면 처리 속성이 없다. PrinterRecord에도 이 정보를 저장하지 않는다. URF 세부 능력도 사용하지 않는다.
- DocumentRenderer는 PWG/URF를 24비트 RGB와 사용자가 선택한 DPI로 만든다. 형식 MIME을 지원한다고 그 형식의 모든 해상도·색상 조합을 지원하는 것은 아니다.
- 해결: 가능한 세부 지원 조건을 조회하여 선택 가능한 조합과 확인되지 않은 조합을 구분한다. 미지원 해상도를 낮춰 보내는 대신 사용자에게 이유를 알린다.
- 표준 참고: PWG IPP Guide의 pwg-raster-document-resolution-supported, pwg-raster-document-type-supported, pwg-raster-document-sheet-back.
  https://www.pwg.org/ipp/ippguide.html

### 10. 변환 시 보존되는 범위를 더 정확히 알려야 함

- DocumentRenderer.kt:400은 픽셀을 8비트 RGB로 내보내고 투명 영역은 흰색과 합성한다. 원본 색상 프로파일·고비트 심도·투명도 보존 경로는 아니다.
- GIF/WebP 등 다중 프레임 입력은 단일 Bitmap으로 읽는다. 전체 프레임을 인쇄하지 않으며 첫 프레임만 사용하는 의미가 현재 선택 UI에 없다.
- TXT는 TextPdfStreaming에서 기본 15pt, Android 글꼴, 자동 줄바꿈으로 새 페이지를 구성한다. 기본 정렬은 가운데이며 각 줄에 정렬을 적용한다. TXT 자체에는 고정 용지 배치가 없으므로 렌더링 규칙은 필요하지만, 다른 편집기에서 보던 배치의 보존을 약속할 수는 없다.
- 해결: 형식별로 꼭 필요한 변화만 짧게 설명하고, 처리하지 못하는 다중 프레임·특수 색상 입력의 동작을 명확히 정한다. 모든 내부 옵션을 사용자에게 노출할 필요는 없다.

### 11. 전송 결과 불확실성과 긴 작업의 제어

- IppClient.exceptionPrintResult는 전송 중 타임아웃·연결 끊김을 일반 실패로 반환한다. 프린터가 이미 작업을 받았을 가능성을 별도로 표시하지 않는다.
- PrintWorkManager.cancel은 이름·인증 대기에서만 동작한다. 이미 진행 중인 문서 준비·전송에는 사용자 취소 기능이 없다.
- 작업은 앱 프로세스의 단일 작업 스레드에만 있다. 백그라운드 서비스나 지속 작업 기록이 없으므로 긴 변환 중 프로세스가 종료되면 유지되지 않는다.
- 해결: '접수 거절'과 '접수 여부 확인 불가'를 구분한다. 준비 취소와 접수된 작업 취소도 구분한다. 실제 백그라운드 인쇄를 지원할지, 화면을 유지해야 하는 기능으로 제공할지 범위를 정한다.

### 12. 입력 검증과 설정 복원

- 확인: MainActivity.kt:3183은 복사 매수의 숫자 파싱 실패도 1부로 처리한다. 너무 큰 숫자가 입력되어 Int 범위를 넘을 때도 사용자가 적은 값 대신 1부를 요청한다. 빈 값 기본 1부와 잘못된 입력을 구분해야 한다.
- 추가 확인 필요: 설정 복원은 실제 MIME·DPI·압축 값이 아니라 Spinner의 위치를 저장한다(MainActivity.kt:3234~3293). 변환 목록과 압축 선택지는 동적으로 재구성되고 선택 리스너가 복원 중에도 동작하므로 화면 재생성 후 의미가 같은 값이 복원되는지 UI 검증이 필요하다.
- 추가 확인 필요: 파일 MIME 검사 완료 전에도 인쇄 버튼이 동작한다. 이전 배치값이 남은 상태에서 새 파일을 선택하고 바로 출력하면 설정 스냅샷의 canLayout이 false가 될 수 있다. 파일 확인 완료 전 전송을 막거나 실제 MIME 판별 뒤 동일 정책으로 다시 검증해야 한다.

## 메모리와 미리보기 점검

확인된 개선:

- FileDocumentPreparer.preview와 prepare는 별도 작업이다. 축소한 미리보기 PDF·비트맵을 실제 전송에 재사용하지 않는다.
- 화면용 PDF 이미지는 최대 900×1600, 사진 미리보기는 최대 변 길이 2048 및 약 200만 픽셀을 기준으로 축소한다.
- 실제 사진 변환은 가능한 경우 1024×1024 타일, PDF와 출력 이미지 생성은 가로 띠, TXT는 페이지 단위로 처리한다.
- 출력 문서는 임시 파일로 준비하고 IPP 헤더와 파일을 순차 전송한다. Digest 해시도 전체 문서를 배열로 복사하지 않는다.
- 실제 출력에서 메모리 부족을 이유로 DPI나 JPEG 품질을 자동으로 낮추는 분기는 확인하지 못했다. 초과 시 오류를 반환한다.
- 미리보기 창 종료·페이지 교체·취소 시 비트맵과 소유 파일을 정리하는 코드가 있다.
- 중복 인쇄 요청을 막는 gate가 있으며, 일반 네트워크 오류 때문에 작업을 자동 재전송하지 않는다. 명시적인 인증 거절 응답에 대한 재시도는 별도다.

남은 한계와 보완:

- IppClient.kt:676은 HTTP 응답 전체를 readBytes로 읽는다. 인쇄 문서 전송은 스트리밍이어도 응답 크기는 제한되지 않는다. 비정상적으로 큰 응답에 대한 상한과 명확한 오류 처리가 필요하다.
- 영역 디코딩을 지원하지 않는 사진은 전체 비트맵으로 읽는 대체 경로가 있다(DocumentRenderer.kt:325). 부족하면 오류를 표시하며, 자동 축소하지는 않는다. 이 한계는 지원 범위에 명시하거나 해당 디코더를 보완해야 한다.
- StreamingRasterPdfWriter의 객체 위치·페이지 번호 목록은 문서 크기에 따라 메모리에서 증가한다. imposePdfTo도 전체 페이지 인덱스와 chunked 목록을 만든다. TXT 전용 PDF 병합기의 디스크 기반 인덱스와 달리 모든 경로가 문서 길이에 무관한 메모리 사용량을 갖지는 않는다.
- 4MiB 제한은 하나의 렌더링 띠에 대한 목표치다. 행 하나가 이 크기보다 넓으면 최소 한 행을 할당한다. Android PDF/이미지 디코더의 내부 메모리까지 제한한다는 뜻은 아니다.
- 정상 종료·예외 정리는 있지만 프로세스 강제 종료 후 남은 작업 캐시를 다음 실행에서 회수하는 코드는 확인되지 않았다. 임시 파일 누적으로 저장 공간이 부족해질 수 있다.

## 이미 사용자가 정한 기본값

흑백 우선 선택은 MainActivity.kt:2244에 남아 있다. 이것은 과거 사용자의 요청으로 정한 기본값이다. 현재의 '원본 색상 유지' 기준을 기본 동작에도 적용하려면 이 정책을 함께 조정해야 한다. 단순히 인쇄 경로의 버그라고 볼 항목은 아니다.

프린터 기본값에 맡긴 단면/양면·품질·해상도는 화면에 기본값으로 표시되며, 앱이 새 값을 선택했다는 뜻은 아니다. 다만 원본 바이트를 유지하는 것과 프린터의 물리적 출력이 원본 화면과 같다는 것은 다르다. IPP 옵션과 문서 내부 명령의 우선순위도 기기에 따라 달라질 수 있다(RFC 8011의 pdl-override-supported 설명).

## 1.0 판단 기준

1. 항목 1~6의 실제 출력 변경·설정 누락·숨은 손실 압축·응답 처리 문제를 먼저 해결한다.
2. 항목 7~12와 메모리 보완 중 지원하는 기능에 해당하는 문제를 해결한다. 제공하지 못하는 조합은 선택 단계에서 명시적으로 제외하거나 이유와 함께 중단한다.
3. 원본 전달은 바이트 동일성, 변환은 선택 형식·DPI·압축·페이지 배치 보존을 확인한다. 미리보기 축소 데이터가 출력으로 넘어가지 않는지도 확인한다.
4. 사용자 실사용 확인 항목: 원본 PDF/사진, 미지원 형식 변환, 페이지 범위만 선택, 모아찍기, 배치 설정 충돌, PostScript MIME 별칭, 큰 사진·긴 TXT, 화면 재생성, 통신 중단 후 재시도 판단.
5. 실제 프린터에서 확인한 형식·옵션 조합을 기록한다. 작업 접수와 종이 출력 완료를 구분한다.
6. 마지막으로 버전과 README를 함께 정리한다. 현재 README 첫머리는 0.9.11이고 앱은 0.9.13이다.

기존 0.9.10 수정 문서에는 단위 테스트 208개 및 휴대폰 내부 변환 검사 46개 통과가 기록되어 있다. 이는 당시 코드와 그 검사 범위에 대한 기록이며, 이번에 발견한 UI→변환→전송 조합이 현재 버전에서 검증되었다는 증거로 사용하지 않는다.

현재 앱에는 원본 전송, 명시적 형식 선택, 고해상도 부분 처리 등 필요한 기반이 있다. 그러나 사용자가 요청한 '보이지 않는 변경이 없어야 한다'는 출시 기준에는 아직 위의 예외가 남아 있다. 버전 숫자를 먼저 1.0으로 바꾸기보다 이 목록을 마무리한 뒤 판단하는 것이 맞다.
