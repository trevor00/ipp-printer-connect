# 0.9.10 수정 내역

0.9.9에 남아 있던 TXT 전체 문서 보관과 최종 JPEG·PNG의 전체 페이지 비트맵 사용을 줄였다. 미리보기는 화면용으로 따로 만들고, 실제 인쇄에서는 사용자가 선택한 해상도와 압축 품질을 유지한다.

## TXT 파일 변환

파일 전체를 먼저 일정 크기의 버퍼로 읽어 인코딩을 검사한다. BOM이 있으면 그 인코딩을 따르고, 없으면 UTF-8을 검사한 뒤 실제 문자 해석 오류가 있을 때만 CP949로 다시 검사한다. 파일 끝에서 인코딩 오류가 발견돼도 서로 다른 인코딩으로 만든 페이지가 섞이지 않도록, 페이지 생성 전에 검사를 끝낸다.

검사를 마친 파일은 다시 열어 조금씩 읽는다. 긴 한 줄도 통째로 읽지 않고 용지 폭에 맞게 나누며, 현재 페이지에 필요한 줄만 보관한다. 페이지 하나를 Android PDF로 저장한 뒤 해당 PDF 생성기를 닫는다.

각 페이지의 글꼴·본문 스트림은 최종 PDF로 복사한다. 이 과정에서 한글 글자를 저해상도 이미지로 바꾸지 않는다. 최종 PDF의 페이지 목록과 객체 위치도 임시 파일에 저장하므로, 모든 페이지와 글꼴 객체를 메모리에 유지할 필요가 없다.

페이지를 합치는 코드는 앱이 직접 만든 단일 페이지 PDF에만 사용한다. 사용자가 선택한 일반 PDF를 이 코드로 해석하지 않는다. 지원하지 않는 Android 생성 PDF 구조를 만나면 글자를 누락하거나 이미지로 바꾸지 않고 실패 이유를 표시한다.

TXT 원문을 그대로 전송할 수 있는 작업은 기존처럼 원본 전송을 유지한다. 원본 파일은 수정하지 않는다.

## 최종 PNG·JPEG 변환

페이지를 작은 가로 띠로 렌더링하고, 픽셀을 한 행씩 압축기에 넘긴다. A4·1200dpi처럼 큰 페이지도 전체 페이지 비트맵 하나를 만들지 않는다. 렌더링 띠와 압축 버퍼의 크기를 제한하지만, 출력할 픽셀 수나 DPI를 임의로 낮추지는 않는다.

PNG는 행 단위 필터와 하나의 zlib 스트림을 사용한다. 압축 결과를 작은 IDAT 청크로 저장하고 DPI와 CRC를 기록한다. PNG의 픽셀 압축은 무손실이다.

JPEG는 공식 libjpeg-turbo 3.2.0을 앱에 포함해 행 단위로 압축한다. baseline sequential 방식으로 인코딩하고, 전체 이미지의 DCT 계수를 보관하는 Huffman 최적화와 progressive 방식은 사용하지 않는다. 선택한 JPEG 품질과 DPI를 유지하지만, Huffman 최적화를 사용하던 이전 출력보다 파일이 커질 수 있다. JPEG 품질 100도 무손실 압축은 아니다.

압축기에서 저장 오류나 취소가 발생하면 해당 작업을 중단하고 자원을 정리한다. 실패한 압축기를 다시 사용하지 않으며, 호출자가 소유한 출력 스트림을 압축기에서 임의로 닫지 않는다.

## 미리보기와 실제 인쇄

미리보기는 기존 화면용 크기 제한을 유지한다. 화면용으로 축소한 이미지는 인쇄용으로 재사용하지 않는다. 문서 배치와 실제 전송 데이터는 선택한 인쇄 설정을 기준으로 다시 생성한다.

## 남아 있는 한계

- 휴대폰의 저장 공간과 메모리, 프린터의 처리 용량에는 한계가 있다.
- 영역 읽기를 지원하지 않는 이미지 형식은 원본 전체를 읽어야 할 수 있다.
- JPEG는 라이브러리의 형식 한계에 따라 가로·세로 각각 65,500픽셀까지 처리한다. 초과하면 자동 축소하지 않는다.
- JPEG·PNG 한 파일로 여러 페이지를 합쳐 전송하지 않는다. 여러 페이지를 처리할 수 있는 다른 출력 형식이 필요하다.
- TXT를 페이지별로 PDF로 만들면서 글꼴 데이터가 중복될 수 있다. 전체 문서를 메모리에 보관하지 않는 대신 파일 크기와 처리 시간이 늘어날 수 있다.
- 폭이 거의 없는 결합문자 등이 한 출력 줄에 과도하게 누적되면 65,536 UTF-16 코드 단위에서 명시적으로 실패한다. 내용을 자르거나 글자 크기를 줄여 계속하지 않는다. 앱이 만든 PDF의 비정상적으로 큰 구문·객체 구조도 검사해 거부한다.
- 앱 내부 변환 성공이나 IPP 작업 접수가 실제 종이 출력 성공을 보장하지는 않는다.

2026-10-20에 확인했다.

- 앱 버전: 0.9.10, versionCode 100
- 단위 테스트: 25개 클래스, 208개 통과, 실패·오류·건너뜀 0개
- 네이티브 JPEG 모듈: arm64-v8a, armeabi-v7a, x86, x86_64 빌드 성공 및 APK 포함 확인
- 앱 APK와 Android 내부 검증 APK: 빌드 성공
- 휴대폰 내부 변환 테스트: 최종 빌드에서 46개 통과, 실패 0개, INSTRUMENTATION_CODE -1
- 휴대폰: Samsung SM-A556S에 기존 데이터를 유지해 업데이트 설치. 설치된 versionName 0.9.10과 versionCode 100 확인
- 실제 프린터 전송·종이 출력: 이번 점검에서는 실행하지 않음

폰에서는 A4(595×842pt)·1200dpi PNG/JPEG를 9917×14033픽셀로 생성하고, 크기·DPI 메타데이터·부분 픽셀을 확인했다. 이 크기는 전체 ARGB 비트맵으로 만들면 약 531 MiB가 필요하지만, 새 경로는 작은 띠를 순서대로 처리한다. 앱 전체의 메모리 사용량이 4 MiB라는 뜻은 아니다.

작은 PNG는 기준 렌더링의 모든 픽셀과 비교해 일치했다. JPEG는 선택 품질 90과 100의 양자화 테이블을 구분하고, 출력 오류·미완성 행·취소·출력 콜백 재진입 처리가 안전하게 끝나는지 검사했다.

한글 TXT는 기존 방식과 새 방식의 페이지 수 및 모든 페이지의 렌더링 픽셀을 비교했다. 0도·90도 내용 회전, 줄바꿈과 아래 정렬이 일치했다. 1,500줄 문서를 100페이지 넘게 생성하고 마지막 페이지의 내용도 확인했다. UTF-16LE·UTF-16BE BOM과 CP949를 읽은 결과도 기준 글자와 일치했다.

단위 테스트에서는 UTF-8 파일 말미의 해석 오류와 CP949 재검증, 매우 긴 한 줄, 청크 경계의 서로게이트·CRLF, PDF 폰트·ToUnicode·본문 바이너리 보존, 객체 참조 재매핑·xref 위치, 잘못된 구조 거부를 확인했다. 생성 도중 오류·취소가 발생했을 때의 임시 파일 정리도 검사했다.

기존 PDF 배치·모아찍기·페이지 범위·프린트 불가 영역, 사진 EXIF·타일 경계, PostScript·PWG Raster·URF·PCL 검사도 함께 통과했다. 테스트 문서는 앱 캐시에만 생성하고 끝난 뒤 정리했다. 휴대폰 설정이나 실제 프린터를 조작하지 않았고, 별도 테스트 APK는 제거한 뒤 실제 앱을 열어 두었다.
